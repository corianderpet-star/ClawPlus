# 工作流 AI 生成与审批流实现解析

## 版本

- 当前整理版本：`0.1.24-alpha.17.2`

## 目标

这次改动围绕三个目标展开：

1. 让用户可以通过对话一键生成工作流草稿，而不是手动从零搭建。
2. 让导入后的工作流稳定可见，节点、连线、视口都能正确落到主画布。
3. 当草稿希望引入 `skill` 或其他外部能力时，从“自动导入”切换为“先审批、再导入”。

## 核心开发思想

### 1. 先生成草稿，再决定是否导入

系统不会直接把模型输出写进正式工作流，而是先生成一个可预览的草稿。这样做的好处是：

- 用户始终有确认权。
- 模型输出可以先经过清洗、补齐、自动排版。
- 即使模型输出不完整，也能退回到基础草稿，不会污染正式数据。

### 2. 边界统一做“规范化”

这次功能里，最关键的一条原则是：**模型输出不可信，存储数据也不能假设天然完整**。  
所以在几个关键边界都做了规范化：

- 生成器返回前：统一校验节点类型、连线、字段结构。
- 导入 store 前：再次序列化/反序列化节点和边。
- React Flow 渲染前：把边的 `type/sourceHandle/targetHandle/animated` 补齐。

这样可以避免出现“预览里能看、导入后线丢了”这类问题。

### 3. 审批流优先于自动化

`skill` 本质上代表外部能力或额外依赖。  
这类能力如果自动进入正式工作流，会带来两个风险：

- 用户并未明确允许新增这个能力。
- 当前环境里可能还没有启用这个 skill。

所以实现上改成：

- 草稿可以“建议”使用 skill。
- 但在导入前必须先审批。
- 如果用户拒绝，系统自动把对应节点退化成普通智能体节点。

### 4. 优雅降级，而不是硬失败

当网关超时、模型没回 JSON、或者审批后的二次生成失败时，系统不会直接把整个流程打断，而是：

- 后端生成基础草稿兜底。
- 前端识别当前是否是审批重生场景。
- 如果是审批重生失败，则保留现有草稿，不强行替换成降级结果。

这能减少用户感知上的“界面突然变了”。

## 架构拆分

### 一、工作流页：入口、导入、主画布恢复

文件：

- `src/pages/Workflows/index.tsx`

职责：

- 增加“一键生成”入口按钮。
- 打开 `WorkflowGenerateDialog`。
- 在导入成功后调用 `importWorkflow`。
- 切换工作流时强制让主画布重新 `fitView`，避免新导入流程落在可视区域外。

关键点：

- 主画布 `ReactFlow` 增加 `key={currentWorkflowId}`，确保导入新工作流时重新挂载。
- `currentWorkflowId` 变化后再次 `fitView`，解决导入后空白画布问题。

### 二、生成弹窗：对话、预览、审批

文件：

- `src/pages/Workflows/WorkflowGenerateDialog.tsx`
- `src/pages/Workflows/nodeTypes.ts`

职责：

- 维护需求对话上下文。
- 加载可选智能体和可用 `skill` 列表。
- 发起 `workflow:generate` 请求。
- 展示预览流程图。
- 展示待审批的 skill 建议。
- 审批后再次生成草稿。

关键点：

#### 1. 预览画布与主画布隔离

弹窗里的预览 `ReactFlow` 使用独立的 `ReactFlowProvider`，避免和主工作流页的上下文互相污染。

#### 2. 审批不是本地硬改，而是“带决策再生成”

审批时不是简单在前端改节点，而是把：

- 当前对话消息
- 审批决定 `approvalDecisions`
- 当前可用 skills

一起重新发给后端，让后端生成最新草稿。

这样能保证：

- 草稿始终是完整一致的结构。
- 审批对上下游节点、提示词、输出连线的影响都能整体重算。

#### 3. 审批失败时保留旧草稿

为了解决你看到的“审批后界面突然变了”，前端现在会识别后端返回的 `draftMode`：

- `agent`：正常由智能体生成。
- `fallback`：后端因为超时或异常退回基础草稿。

如果当前是审批后的重生成，而且拿到的是 `fallback`，前端会：

- 保留当前预览草稿。
- 给出错误提示。
- 不把界面替换成基础版本。

#### 4. 布局容器固定头尾区域

弹窗中的头部、左侧工具区、右侧预览头部、底部按钮区，都补了 `shrink-0`。  
中间滚动区则使用 `overflow-hidden` + `overflow-y-auto`。

这样在审批消息变长时：

- 聊天列表滚动。
- 预览区域滚动。
- 头部和底部按钮不会被挤没。

### 三、Store：导入、保存、加载统一序列化

文件：

- `src/stores/workflow.ts`
- `src/types/workflow.ts`

职责：

- 统一工作流的持久化结构。
- 统一运行态数据清理。
- 导入/保存/加载时补齐边和节点。

关键点：

#### 1. 边的结构统一

新增了对边字段的显式处理：

- `type`
- `animated`
- `sourceHandle`
- `targetHandle`
- `label`

这解决了 React Flow 对边数据依赖比较敏感，字段缺失时不显示连线的问题。

#### 2. 节点运行态与配置态分离

存储前会清掉：

- `runStatus`
- `runResult`

这样导入后的工作流不会带着上一次运行残留状态。

#### 3. 导入前生成唯一工作流 ID

`prepareImportedWorkflow()` 会在导入时处理：

- 唯一 ID
- 标题默认值
- 时间戳
- 节点与边的结构整理

避免新草稿导入时覆盖已有工作流。

### 四、主进程生成器：模型输出清洗与审批建议

文件：

- `electron/services/workflow/workflow-generator.ts`
- `electron/main/ipc-handlers.ts`
- `electron/preload/index.ts`

职责：

- 接收前端对话与审批信息。
- 生成 prompt 调用编排器。
- 解析模型返回 JSON。
- 清洗节点和边。
- 识别 skill 建议并生成审批项。
- 必要时生成基础草稿兜底。

关键点：

#### 1. Prompt 里显式注入可用 agent 与 skill

生成器会把：

- 当前选中的 agent
- 当前可用 agent 列表
- 当前可用 skill 列表

一起写进 prompt，目的是让模型尽量优先复用现有能力，而不是随意幻想不存在的节点。

#### 2. 先解析结构，再清洗结构

即使模型返回了 JSON，也不会直接信任，而是进入 `sanitizeWorkflow()`：

- 过滤非法节点类型。
- 修正无效 agentId。
- 修正 inputMappings 的来源节点。
- 过滤无效连线。
- 没有 trigger 时自动补 trigger。
- 没有有效 edges 时自动按顺序补线。

#### 3. skill 的自动补全与审批

当模型产出 skill 节点但没写 `skillId` 时，不再直接降级，而是先根据文案推断一个建议值，例如：

- `publish-xiaohongshu`
- `publish-wechat-official-account`

然后把它作为“待审批 skill”返回给前端。

#### 4. 用户拒绝 skill 时自动退化为 agent

如果用户拒绝审批，生成器会在重生草稿时把 skill 节点改成普通 agent 节点，并保留：

- 原节点标题
- 原描述
- 原输入映射
- 原超时与重试配置

这样不会因为拒绝 skill 而让整个流程断掉。

#### 5. 标记草稿模式

后端增加 `draftMode`：

- `agent`
- `fallback`

这个字段不是给业务功能直接用的，而是给前端做“失败时如何保留界面状态”的判断依据。

## 一条完整链路

### 场景：用户要“自动生成并发布小红书”

1. 用户点击工作流页的一键生成。
2. 弹窗选择智能体，输入需求。
3. 前端收集可用 skills，一起调用 `workflow:generate`。
4. 主进程拼 prompt，调用智能体生成 JSON 草稿。
5. 生成器清洗节点与边，并识别“发布到小红书”更适合 skill。
6. 如果这个 skill 需要确认，就返回审批项而不是允许直接导入。
7. 用户点击同意或拒绝。
8. 前端把审批决定回传，再次请求生成最新草稿。
9. 草稿确认无误后导入 store。
10. store 序列化并保存，主画布重新挂载并 `fitView`。

## 为什么这次能修掉“导入后不显示”的 bug

之前的问题本质上不是单点 bug，而是多个边界同时缺乏兜底：

- 草稿边结构不统一。
- 导入后的边没有再次规范化。
- 主画布切换 workflow 后没有稳定地重置视口。
- 预览画布和主画布上下文过于接近，增加了状态干扰概率。

这次修复把这些问题拆开分别处理，所以表现会稳定很多。

## 目前仍然保留的取舍

### 1. 审批仍然是对话式，而不是任务面板式

现在审批更偏“轻量闭环”，优点是改动小、和现有对话体验一致。  
缺点是如果未来审批项更多，可能需要独立的审批队列 UI。

### 2. skill 推断仍然是启发式

`deriveSuggestedSkillId()` 目前是规则推断，不是严格的技能检索系统。  
优点是实现简单、速度快；缺点是复杂业务场景下命中率还可以继续提高。

### 3. 兜底草稿仍然偏保守

当模型不可用时，兜底草稿优先保证“能看、能改、能导入”，而不是“业务上百分之百贴合”。

## 后续可继续优化的方向

1. 审批后增加“重试生成”按钮，而不是必须重新点击审批。
2. 将缺失 skill 的审批和“安装/创建 skill”向导打通。
3. 为生成器增加更强的技能检索，而不是仅靠关键词推断。
4. 为预览与导入增加端到端自动化测试。

## 总结

这次实现的核心不是“把 AI 接进来”这么简单，而是把一条完整的产品链路做稳：

- 对话生成
- 结构清洗
- 自动排版
- 审批拦截
- 导入落库
- 主画布恢复
- 异常兜底

本质上，这是一次围绕“可信草稿”和“安全导入”展开的工作流编辑器增强。
